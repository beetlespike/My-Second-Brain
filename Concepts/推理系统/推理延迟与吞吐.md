# 推理延迟与吞吐

流式问答有两段等待。用户发出问题后，等到第一段输出的时间通常记为首 token 延迟（TTFT）。从客户端量，它可以包括排队、网络和 [prefill](Prefill与Decode.md)。第一个输出到了以后，还要等剩下的文字逐段出现。若按输出 token 摊算，可以用首尾输出的时间差除以首个 token 以外的输出 token 数。只有一个输出 token 时，这项平均值没有定义。

## 总吞吐高，单条请求也快吗？

假设[连续合批](连续合批.md)每轮给 32 条活跃请求各产一个 token，一轮耗时 10 ms。系统每秒产出 3200 token，每条活跃请求平均每秒拿到 100 token。如果扩到 64 条后每轮变成 15 ms，总吞吐约 4267 token/s，每条平均约 67 token/s。这是固定步时的算例。真实服务要在同一观察窗口统计实际产出。

比较服务配置时，保留相同的请求和到达时间。可以同时报告首 token 延迟、输出 token/s 和延迟分位数。记录缓存是冷是热，便于理解[前缀缓存](前缀缓存.md)与[分块预填充](分块预填充.md)改变了哪一段等待时间。
